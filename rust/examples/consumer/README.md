# A starter crate

This crate builds decoders from a schema split across two `.proto` files and decodes one message
twice: first with the [arena decoder](https://docs.rs/rapidproto), then with the
[streaming decoder](https://docs.rs/rapidproto/latest/rapidproto/stream/index.html). In the
streaming decode, the `origin` sub-message goes on to the arena decoder.

To start a crate of your own, copy [`Cargo.toml`](Cargo.toml) and [`build.rs`](build.rs). The
two path dependencies only work inside this repository. In your crate, require `rapidproto` and
`rapidproto-build` at one exact version with `=`, as the [Rust quick start](../../../README.md#rust)
does. Code generated by one release of [`rapidproto-build`](https://docs.rs/rapidproto-build)
expects `rapidproto` from that same release.

The crate belongs to the workspace in `rust/`, so run it there or in a directory below it:

```sh
cargo run -p consumer-example
```

```text
decoded Shape { name: "hi", origin: Point { x: 3, y: 4 }, kind: Circle, sides: [3, 4, 5] }
streamed the same demo.Shape; its fields agree with the arena decode
```

## Schema and build script

```rust
fn main() {
    rapidproto_build::Config::new("crate::schema")
        .stream(true)
        .serde(std::env::var_os("CARGO_FEATURE_SERDE").is_some())
        .include("proto")
        .compile(&["proto/message.proto"])
        .expect("generate decoders");
}
```

[`proto/message.proto`](proto/message.proto) is a proto3 schema in `package demo`. It imports
[`proto/types.proto`](proto/types.proto) for `Point`, the type of `Shape.origin`. Without
`.include("proto")`, that import wouldn't resolve.

[`src/main.rs`](src/main.rs) includes the generated file inside `mod schema` and imports from it:

```rust
mod schema {
    include!(concat!(env!("OUT_DIR"), "/message.rs"));
}

use rapidproto::Arena;
use schema::arena::demo::{Point as ArenaPoint, Shape as ArenaShape};
use schema::common::demo::{Kind, KindClass};
use schema::stream::demo::{shape_stream, Shape};
```

The generated file takes its name from the first schema passed to
[`compile`](https://docs.rs/rapidproto-build/latest/rapidproto_build/struct.Config.html#method.compile),
and the
[module path](https://docs.rs/rapidproto-build/latest/rapidproto_build/struct.Config.html#method.new)
`"crate::schema"` in `build.rs` has to name this `mod schema`. Renaming the arena types on import
frees `Shape` for the streaming decoder's type.

## The two decodes

`main.rs` decodes `SHAPE_WIRE` twice. Those 20 bytes hold the `Shape` from the output above. A
trailing field 99 isn't in the schema, and both decoders pass over it. The arena half is plain
[accessor](https://docs.rs/rapidproto/latest/rapidproto/example/index.html#accessors) reads, a
`match` on `kind().classify()` (that's what `KindClass` is for), and a check that a 5-byte prefix
of the input fails to decode.

The streaming decoder is the one to reach for when you care about a handful of fields in a big
message ([how the two compare](../../../README.md#two-decoders)). Its half of `main.rs` takes more
code:

```rust
let mut parts = ShapeParts::default();
Shape::new(SHAPE_WIRE)
    .and_then(|stream| {
        stream.decode(shape_stream!(&mut parts; {
            name => |p, n| {
                p.name = n.to_str()?.to_owned();
                Ok(())
            },
            origin => |p, pt| {
                let sub_arena = Arena::new();
                let point = ArenaPoint::decode(pt.bytes(), &sub_arena)?;
                p.x = point.x();
                p.y = point.y();
                Ok(())
            },
            kind => |p, k| p.kind = k.0,
            sides => |p, v| p.sides_sum += v,
        }))
    })
    .expect("stream demo.Shape");
```

Once a streaming decode returns there's no message left to read. The handlers copy what they need
into `parts`, a `ShapeParts` declared in `main.rs` itself, with `kind` taking the plain `i32`
inside the enum value (`k.0`). The `&mut parts;` form of the macro passes `parts` to every handler
as `p`. Each of these handlers returns `()`, or `Result<(), DecodeError>` where it can fail
([what else a handler may return](https://docs.rs/rapidproto/latest/rapidproto/stream/index.html#handlers)).
`Shape::new` returns a `Result` too, though it only rejects input longer than `u32::MAX` bytes.

In the `origin` handler, `pt` is a
[stream struct](https://docs.rs/rapidproto/latest/rapidproto/stream/index.html#what-a-handler-receives)
for the `Point`, and `pt.bytes()` returns the slice of `SHAPE_WIRE` that encodes it. The handler
decodes that slice into a throwaway
[arena](https://docs.rs/rapidproto/latest/rapidproto/struct.Arena.html) and keeps only `x` and
`y`, so the arena can go when the handler returns. If that decode fails, the `?` passes its error
out of the handler, and the streaming decode returns it.

`main.rs` calls `expect` on both decodes because `SHAPE_WIRE` is a constant. With real input you'd
return the error instead.

## Serde

```sh
cargo run -p consumer-example --features serde
```

This build prints a third line:

```text
as JSON: {"name":"hi","origin":{"x":3,"y":4},"kind":1,"sides":[3,4,5]}
```

The crate's `serde` feature turns on RapidProto's serde support. `build.rs` asks for `Serialize`
impls only when Cargo sets `CARGO_FEATURE_SERDE`, as the
[`Config::serde`](https://docs.rs/rapidproto-build/latest/rapidproto_build/struct.Config.html#method.serde)
docs show. In the JSON, `kind` comes out as the number `1`
([how messages serialize](https://docs.rs/rapidproto/latest/rapidproto/#serde)).
